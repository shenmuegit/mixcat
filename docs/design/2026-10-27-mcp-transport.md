# 本机 MCP 空闲连接竞争修复

关联 [Issue #17](https://github.com/shenmuegit/mixcat/issues/17)。诊断基线：`e73f682ed5c23585d7e197594437ca8d2804c9f4`。

## 原始问题与复现

项目管理真实节点验收的 17 次 MCP 尝试中，文档创建和工作项读取各失败一次。原生会话及日志都记录为发往本机 Mixcat 网关的 `Transport send error` / `HTTP request failed`，没有业务错误结果。文档只在后一次成功调用时创建，失败调用没有对应的持久业务事件。

| 调用 | 开始时间（UTC） | 距上次调用完成 | 结果 |
| --- | --- | --- | --- |
| `update_project_item` | 2026-10-26 17:27:36.035 | 5.722 秒 | 传输失败，重试成功 |
| `get_project_item` | 2026-10-26 17:28:46.411 | 5.967 秒 | 传输失败，重试成功 |

使用同一原生 Codex `0.164.0-alpha.11.1` 和 Code Mode，通过本机受控 Responses SSE 返回工具调用，避免真实模型的随机思考时长和主动重试掩盖问题。只读网关处理、真实 TCP/HTTP 与原生 MCP 客户端均实际运行。

- 普通间隔扫描未失败；将连续调用集中在上次响应后 5,990 毫秒，17 次尝试中复现 4 次同签名传输失败，只有 13 次进入工具处理。
- 网关在 Node.js 24.19.0 下使用默认 5,000 毫秒 keep-alive 超时及 1,000 毫秒缓冲。四次失败均紧邻旧连接关闭，且没有新的 HTTP 请求进入处理。
- 其中一次：上次响应在探针时间 29,456 毫秒完成；35,451 毫秒发出受控工具调用；35,458 毫秒旧连接关闭；35,460 毫秒原生客户端报告传输失败。随后新建连接的调用成功。
- 单变量对照只将响应设为 `Connection: close`，相同 17 次原生调用全部成功。

这确认了网关空闲超时与客户端复用连接之间的竞争。历史两次错误的签名及时间特征一致，但原验收没有保存 TCP 时序，不能将后续探针的逐连接证据冒充原始抓包。[Node.js 24 的 HTTP 文档](https://nodejs.org/download/release/v24.19.0/docs/api/http.html#requestreusedsocket)也说明了服务端关闭与客户端复用连接重叠时的重置风险。

## 处理方式

Mixcat 的网关采用无会话、每请求独立的 MCP transport。现在对成功及错误响应明确发送 `Connection: close`，由 HTTP 服务端在完整响应结束后关闭连接。下一次调用新建本机 TCP 连接，不再把一个即将到期的空闲连接交回客户端连接池。

代价是每次调用多一次本机 TCP 建连。没有新增自动写入重试；身份验证、来源校验及已有持久回执继续决定业务操作是否受理。该改动针对 Mixcat 的本机 HTTP 网关，不解决其他远端 MCP 服务的网络故障。

## 验证入口

- `tests/mcp.test.ts`：使用保活客户端验证完整响应、显式连接关闭、后续调用不复用旧连接及身份隔离；该回归在修复前失败，修复后通过。
- `tests/project-items-mcp.test.ts`、`tests/dynamic-edge-mcp.test.ts`：覆盖实际 HTTP 写入、回执重放、条件边交接和并发调用。
- `scripts/verify-mcp-transport-native.ts`：设置 `MIXCAT_CODEX` 和 `MIXCAT_MODEL_CATALOG` 后，以 Node 24+ 和 `--import tsx` 执行。后者指向已有原生模型目录 JSON；脚本仅提取 Code Mode 模型元数据，在项目内建立一次性本机模型服务，不复制账号身份，也不请求真实模型服务。验证 17 次间隔调用及 2 次并行调用，包含 8 次带原生来源标识的写入工具调用。业务持久化由上述集成测试验证。

原始诊断与对照报告保存在本项目 `.runtime/implementation/mcp-transport/`，不提交原生会话、账号数据或捕获的请求正文。

修复后的正式代码通过原生验证：19 次 MCP 调用（8 次写入工具调用、2 次并行读取），0 次传输失败，未依赖模型重试。报告：`native-check-NkS0rG/result.json`。相关定向回归 23/23、类型检查及构建通过；完整回归与正式客户端验收结果随 PR 记录。
