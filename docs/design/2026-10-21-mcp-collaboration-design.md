## 1. 已确认的目标和范围

Mixcat 通过本地 MCP 为独立 Codex 会话增加协作能力。Agent 判断下一步工作和接收者；Mixcat 验证来源、持久保存内容、安排目标会话执行并保留原始记录。

确认的产品规则：

- 每节点复用自己的原生 Thread 和历史，cwd 始终为项目目录。
- 用户和 Agent 的业务内容自由，不要求 summary、verdict 或统一业务 Schema。
- 条件边是自然语言协作指导。Agent 可以联系同项目中没有连线的其他节点，并留下选择理由。
- 发送消息不结束来源任务。来源可以继续工作，也可以自然结束当前原生轮次，等回复到达后在原会话继续。
- 回复由 Agent 显式发送并关联原消息；普通输出、工具日志和每轮结束不会自动跨节点广播。
- 审查是一种可选职责，无默认审查门槛、固定角色名称或必经路线。用户明确要求审查时才按要求组织；缺少承担者时不能声称要求已满足。
- 每节点继续只有一份权威的多值运行状态。等待回复、消息投递记录和项目汇总都不增加第二层暂停锁。
- 单次发送一个目标，可连续发送多次并让不同节点并行执行。本版不提供自动汇合、自动合并文件或多目标原子发送。
- 保留原生工具、审批和输入能力；新增 MCP 权限仅管理 Mixcat 协作工具，不能用来关闭 Codex 原生能力。

不在本版中增加服务进程、消息中间件、自然语言真假解释器、默认审查器、自动转发所有输出、自动创建工作树或新的项目发布流程。浏览器控制桥、MCP App UI 和交互式终端沿用各自后续设计。

## 2. 架构与唯一事实来源

继续使用现有 Electron 主进程、业务 worker、WorkflowEngine、项目级 Codex app-server、本地 MCP 网关和 ProjectStore。

~~~mermaid
sequenceDiagram
    participant A as 来源节点 A
    participant M as MCP / WorkflowEngine
    participant D as 项目 SQLite
    participant B as 目标节点 B
    A->>M: send_message
    M->>D: 提交消息、目标任务、输入历史
    D-->>M: 提交成功
    M-->>A: 稳定消息编号及受理回执
    M->>B: 可执行时，在原 Thread 开始新 Turn
    B->>M: send_message，携带 reply_to
    M->>D: 提交回复及 A 的接收任务
    M->>A: A 可执行时，在原 Thread 继续
~~~

消息记录保存“谁发送了什么、为什么、回复了哪条消息”；StoredTask 保存接收方执行事实；StoredNode.status 决定该节点当前能否执行。get_delivery 从任务记录生成执行状态视图，不维护另一套独立可变的执行状态。

MCP 和用户界面应共用经过验证的节点、边及消息受理操作，但保留真实来源。不能把 Agent 请求伪装成用户命令来继承用户身份或额外权限。网络和原生 RPC 等待不得占用项目状态提交区间。会话身份检查保证宿主入口的来源关联，不改变现有可信本地 OS 用户边界，不宣称已经隔离 Agent 对项目控制目录的原生文件访问。

## 3. 工具目录

| 工具 | 作用 | 本版行为 |
| --- | --- | --- |
| get_project_context | 了解协作环境 | 当前输入来源、项目目标、自己和其他节点、条件边、状态、配置版本及所选能力 |
| send_message | 向节点发送或回复 | 持久提交后进入目标队列；不写来源 terminal、不结束来源 Turn |
| get_delivery | 查询一次发送 | 受理事实、目标任务状态、输出引用、关联回复、错误或待核对情况 |
| read_history | 查询原始记录 | 按项目、节点、任务、消息关联分页查询；保留作者与原始内容 |
| update_workflow | 创建和调整工作流 | 新建/更新节点、新建/更新条件边；沿用授权、版本和忙碌检查 |

旧 handoff 和 complete_task 保留兼容。本版不重新解释已保存的终结动作、历史交接或原项目的工具配置。

工具是否可见和可调用均沿用节点的 Mixcat 工具授权。新增工具不会通过项目迁移自动获得授权；用户在节点配置中选择，已获授权的流程编辑者按第 9 节明确的委派范围配置节点。Agent 不得借 update_workflow 为自己或其他节点扩授流程修改权。用户界面的能力列表同步识别新增工具；能够接收消息不等于已经获准主动发送，来源可从节点目录识别目标是否具备回复工具。

## 4. get_project_context

输入默认空对象；可选 include_capabilities=true，用于创建或调整节点前查询可选模型、技能及插件。

默认返回：

- project：项目编号、名称、目标、目录和当前汇总状态。
- self：当前节点编号、名称、职责、配置版本、所选模型/技能/插件、可用 Mixcat 工具。
- task：本次任务编号和原始输入，以及来自用户、节点、系统或未知的来源。
- incoming_message：如本次任务由协作消息触发，提供消息编号、来源节点、reply_to 和附件引用；用户直接输入不伪造节点消息。
- nodes：同项目活动节点的编号、名称、职责、运行状态、配置版本和能力摘要。
- edges：有向边的编号、来源、目标、自然语言条件和 revision。配置边与实际发送历史分别返回。
- collaboration_rules：本规格中稳定的协作说明，不夹带某个项目不存在的审查步骤。

默认响应以增加字段的方式扩展，保留旧 project、task、nodes、remainingSteps 字段及兼容含义；新普通消息不启用旧演练步数上限。默认查询只读后台已有状态，不等待账号连接、模型推理或插件目录扫描。include_capabilities=true 才调用已有原生目录查询；此等待在状态提交区间之外，部分来源失败可分别报告，不能把失败伪装为空目录或阻塞默认查询。

能力摘要说明配置选择；不能据此宣称每个插件账号可用或工具执行一定成功。原始会话全文通过 read_history 查询。

## 5. send_message

### 5.1 输入与回执

~~~json
{
  "request_id": "lookup-payment-docs-01",
  "to_node_id": "research",
  "content": "请核对支付接口是否支持退款并提供资料。我继续处理页面布局。",
  "reason": "资料节点负责查找和核实接口资料",
  "attachments": [],
  "reply_to": null,
  "route": {
    "edge_id": "implementation-to-research",
    "edge_revision": 2
  }
}
~~~

| 字段 | 必需 | 约定 |
| --- | --- | --- |
| request_id | 是 | 来源节点生成的稳定请求编号，沿用命令编号的 1–128 个字母/数字/下划线/连字符限制；同一逻辑发送的重试复用，主动另发使用新编号 |
| to_node_id | 是 | 同项目中存在且未删除的其他节点；本版不向自己发送来自动续跑 |
| content | 是 | 任意 JSON 值，包括字符串；不按业务 Schema 验证，不改写原文 |
| reason | 是 | 简短的目标选择理由；描述决策，不要求模型提供内部推理过程 |
| attachments | 否 | 项目文件或已经登记的附件引用，由宿主保存本次发送的版本 |
| reply_to | 否 | 被回复的消息编号；省略或 null 表示普通发送 |
| route | 否 | 所依据的边编号与读取的 revision；未沿配置边选择可省略 |

来源 project/node/task/thread/turn/call 只能由接入层和实际原生执行关系确定，不能由上述参数声明或覆盖。消息编号由 Mixcat 分配，与接收任务编号分别保存。

成功回执只包含稳定事实：

~~~json
{
  "accepted": true,
  "message_id": "message-uuid",
  "target_task_id": "task-uuid",
  "accepted_at": "2026-10-21T00:00:00.000Z"
}
~~~

accepted 表示数据库已提交，不表示目标已启动、业务成功或整个项目完成。实时情况用 get_delivery 查询。

MCP 外层保持现有请求大小和字段类型检查；业务正文不增加内容模板。原始 content 独立保存，传给原生会话时按原生支持的输入类型构造：字符串保留原文，其他 JSON 提供对应文本表达和原始记录引用。接入提示与来源元数据不得覆盖原始正文，也不得把节点输入标成用户本人输入。

### 5.2 受理与幂等

唯一受理键为项目、来源节点、request_id；与 update_workflow 的操作回执分别命名，不能跨工具混用。

1. 校验节点身份、工具授权、真实 Thread/Turn/call 关联和输入参数。
2. 先查询持久回执。相同键与相同请求内容返回原回执；相同键但内容不同返回 REQUEST_CONFLICT。对象键排列不产生新消息，字符串和数组顺序必须保持精确比较。
3. 新写入要求来源任务仍可执行，尚未提交终结动作，且未被暂停/停止/关闭或存储故障拦截。
4. 核验目标、回复关联和可选条件版本；准备附件快照。
5. 完成异步等待和附件准备后，重新核验身份授权、来源执行/控制状态、目标存在及当前配置、条件版本和受理键。然后在候选状态同时增加消息记录、目标 queued 任务和带来源的输入历史，再通过 ProjectStore 提交。
6. 提交成功才发布 UI 变化、返回受理并唤醒现有调度器。消息固定受理时两端节点名称和目标配置版本；之后重命名不会改写旧来源标签。

已受理请求的合法重试不因目标后来暂停、条件更新、文件变化或节点归档而重做；先返回原受理事实。原来源 Turn 的关联重试，或同来源节点在合法续接 Turn 中使用原 request_id，均不得创建第二个目标任务。原生调用标识还要与 request_id 关联，避免同一实际调用用不同编号重复提交。

同一内容使用新的 request_id 是新消息，不能用正文相似度去重。重试时在命中回执后不重新读取附件；要发送修改后的文件必须使用新编号。回执随消息持久保存，不能仅依赖当前 CommandDispatcher 的进程内 Map。

若提交成功但返回回执失败，可通过原 request_id 查询或重试；不能从网络超时推断发送失败。此保证限于消息受理，不宣称原生工具和外部副作用全局恰好执行一次。

### 5.3 调度、回复与等待

- 目标空闲：按现有调度流程启动或恢复其 Thread，创建新 Turn。
- 目标忙碌：与用户输入共用该节点 FIFO 队列，不插入当前 Turn、不抢占用户输入。
- 目标暂停：保存并排队，返回受理；不自动启用。
- 来源还可独立工作：继续原 Turn。
- 来源需要回复才能继续：正常结束当前 Turn。回复到达后排队并在原 Thread 中开启下一轮。
- 本版不提供保持来源 Turn 占用的阻塞式 wait 工具，也不增加 waiting_reply 节点控制状态。
- 回复必须由原消息的目标节点发给原消息的来源节点；服务端校验 reply_to 与双方对应。向第三个节点转送信息是新的发送，不冒称原请求的回复。
- 同一消息可以有多条有意发送的回复，每条使用独立 request_id；没有基础设施自动生成的“收到”“已完成”往返。
- 一次回复的接收任务不能被默认当作新的求助请求；是否再次发送由实际任务需要决定。
- 普通 Turn 的结束只完成当前执行，不表示整个项目目标已完成。

来源节点后来失败、停止或被删除，不撤回已提交的普通消息。项目级“停止本轮”仍可按现有规则取消其作用范围内尚未执行的目标任务；这是明确用户控制，不能伪装成未发送。消息与任务结果均保留。

回复时若原来源节点已删除，返回 TARGET_UNAVAILABLE，保留回复者当前会话输出，不自动恢复节点、不改投其他节点。删除有未完成接收任务的节点继续沿用现有阻止规则。

## 6. 条件边和协作要求

配置边说明预期关系，发送历史记录实际发生的协作。自然语言条件由 Agent 判断，后台不把模型判断包装成确定性规则验证。

- Agent 优先参考职责和条件；允许没有边的直接发送。每次发送都保留 reason。
- 引用 route 时，边必须从实际来源指向指定目标，revision 必须是当前版本。失效或删除返回 ROUTE_CHANGED，不能静默改成无边发送或换目标。
- 受理时由后台复制边编号、revision、当时条件和两端节点，不相信调用者自己提供的条件文本。
- 受理后编辑/删除条件边不改变旧消息、旧接收任务或历史选路记录。
- 多条件适用时，Agent 选择适合的目标；需要多方参与时分别发送。各次发送独立提交，没有隐含的优先级、广播或自动汇合。
- 条件不匹配时可依据职责直接选择；信息不足时向用户说明或请求补充，不编造条件已经满足。

用户明确的任务要求仍是协作依据。没有审查要求时可直接完成。明确要求独立审查但没有承担者时，可以选择合适现有节点，或在具备授权时创建节点；无法完成要求时如实说明。协议不新增强制审查节点、默认二次审查或项目级硬编码审批步骤。

## 7. 附件、原始内容与版本

附件项二选一：项目内普通文件的相对 path，或已经由宿主登记的 artifact_id。目录、项目外路径、目录链接、ADS 和保留控制路径按现有文件接入规则拒绝；登记过的受控附件通过编号解析，不开放任意控制目录读取。

发送受理前，将文件内容复制到项目内受控成果目录，记录 SHA-256、大小、名称和相对存储引用。以保存的快照字节作为本次发送版本，目标查看该快照；来源文件后续改变不替换旧消息的附件。任意 JSON 正文中的路径只按正文保存，不会自动触发文件读取或固定版本。

附件文件先准备，数据库再登记；任一附件准备失败或数据库提交失败均不能返回已受理。未登记的孤立文件不能参与投递，不自动删除归属不明文件。快照不保证多个源文件在同一时刻被读取，也不自动冻结项目目录。

保留原始 JSON 和附件，不以摘要替代。无法直接输入当前模型的附件保留为文件引用并明确可用形式，不声称所有媒体都可被模型直接理解。选用审查工作流时，结论应关联实际收到的消息和快照；自动判定结论失效、自动复审及整个工作区版本冻结不在本版。

## 8. 查询、历史与可见性

get_delivery 接受 message_id，或当前来源节点的 request_id，二选一。返回原受理回执、该消息关联的接收任务尝试及当前执行状态、任务输出引用、失败/待核对原因及关联回复索引。查询仅限调用者当前项目；不存在与无权访问不能返回别的项目内容。回复列表通过 read_history 按 reply_to 分页查询。

read_history 的可选过滤为 node_id、task_id、message_id、reply_to；省略节点过滤时查询当前项目。分页默认 50 条，上限 200 条，返回 next_cursor。按现有已知时间、未知时间、序号和编号的稳定规则排序。游标绑定过滤条件、排序位置和本次查询的序号上界，新增消息在下一次新查询中读取，不能重复或遗漏同一遍历中已有的条目。

返回原始输入、原始输出或工具事件，以及来源、节点名称快照、时间和原生关联。流式条目可继续更新；不承诺跨页数据库快照，不补造缺失的作者或时间。此接口只对返回结果分页，首版继续使用现有 SQLite JSON 全状态存储，不宣称已实现数据库分表或无限历史规模。

界面沿用输入在右、输出在左的布局：接收节点显示“来源节点 → 当前节点”及原文，发送节点保留实际工具发送事件和目标，点击回复关联可定位原消息。暂停、排队、已开始、失败和待核对来自实际记录，不能靠 Agent 的自然语言自报改写。

## 9. update_workflow

延续现有流程编辑能力和权限，本版增加明确 operation，支持 save_node 与 save_edge；旧的单 node 参数形式继续映射到原行为，不改变旧授权。

- save_node：新建或更新节点，包含名称、职责、模型、skill/plugin 选择、Mixcat 工具、配置 revision；新节点可给初始位置，已有节点保持布局。可选 related_to 和 condition 复用“创建关联节点”操作，节点与初始边在一次提交中建立。
- save_edge：新建或更新有向条件边，包含两端、自然语言条件、编号及 revision。
- 新 operation 形式的两种操作都携带 request_id，持久记录成功受理键和规范化请求，重试返回原结果；同键不同内容拒绝。旧单 node 形式不新增必填字段，保持旧行为，不将其进程内旧回执冒称为新版跨重启保证。
- 新 operation 的工具授权按“目标原有授权”和“本次新增授权”比较：保留目标已有工具不算新授予；新增 send_message、get_delivery、read_history 必须属于实际编辑者已经获准使用的工具，新建和既有目标均适用。旧工具的可授予集合维持兼容规则，任何形式都不得从无到有授予 update_workflow。新 operation 可在保留目标已有流程编辑权的情况下修改普通配置；旧单 node 形式继续采用原权限判断。该范围直接由现有 tools 列表计算，不新增委派开关或授权状态层。
- 现有活跃/排队任务限制、节点删除保留历史规则、配置版本检查继续生效。Agent 修改图不能覆写忙碌节点配置或绕过授权。
- 模型、技能、插件来自 include_capabilities 查询的真实目录。用户可选择原生默认模型；无法读取目录时明确报告错误，不能把杜撰条目记为已激活。
- 新消息受理时固定目标节点配置版本。任务排队后不静默换成另一套职责、模型或工具；现有忙碌配置保护保持这一约定。
- 参数过期返回 REVISION_CONFLICT，等待调用方重读；不能以重试之名覆盖用户在界面上的修改。
- 本版不增加 Agent 删除节点/边工具。用户仍可使用现有删除入口；自动删除可在出现明确需求后单独扩展。

UI 与 MCP 复用同一套已校验操作。节点、边和操作回执先提交后发布；不能继续使用可能在保存失败后留下候选内存改动的编辑路径。成功回执可在原请求重放或合法续接中读取，只有真正的新变更才要求来源当前仍活跃且未终结。

## 10. 旧工具、数据兼容与恢复

| 行为 | 普通 send_message | 兼容 handoff |
| --- | --- | --- |
| 是否写来源 terminal | 否 | 是 |
| 何时可进入目标队列 | 受理提交成功后 | 来源 Turn 确认成功后 |
| 来源是否可继续发送 | 是，直到自然结束或提交终结动作 | 沿用一次终结动作限制 |
| 来源后来失败 | 记录来源失败，保留已提交消息与目标事实 | 沿用待核对规则，不释放未确认交接 |
| 是否固定审查角色 | 否 | 不增加新规则；旧节点职责原样保留 |

complete_task 保留现有结果/阻塞报告语义，不成为普通聊天的强制出口。默认模板的职责只是可编辑模板，协议不能依赖 plan、implement、review 等固定编号。新工具说明应准确区分发送、回复、终结和用户暂停。

项目数据增加消息记录及工作流编辑回执集合并升级为 schema version 3；读取 v1/v2 时补空集合，不根据旧文本猜测 reply_to、条件版本或作者。原 handoffs、terminal、Thread、历史和成果引用保持不变。旧客户端遇到新版本按现有规则明确拒绝，不丢弃新字段后继续写入。

重启时：已受理、尚未派发且目标允许执行的 queued 任务可恢复调度；已确认暂停的任务保持暂停；已经派发但结果不明的执行进入 needs_reconciliation，不因消息幂等而盲目重跑。既有任务未知状态仍阻止同节点后续自动执行，防止重复外部副作用。

用户确认重试接收方执行时，创建新的任务尝试，保留 incoming_message_id、原始来源、reply_to 和附件快照，并记录前次尝试编号；不创建新的发送消息、不重读来源文件。原受理回执里的 target_task_id 始终指向首次接收任务，get_delivery 另列全部关联尝试及当前状态。原始输入仍归实际来源节点，用户触发的重试另记控制事件，追加的续接说明归系统；不能把重试后的正文改称用户原话。回复继续关联原消息，已经发送过的回复不会因重试自动再发。

主要错误使用稳定 code 与可读说明：REQUEST_CONFLICT、TARGET_UNAVAILABLE、INVALID_REPLY、ROUTE_CHANGED、REVISION_CONFLICT、SOURCE_NOT_ACTIVE、PERMISSION_DENIED、STORAGE_UNAVAILABLE。预期业务错误不伪装成连接故障；不自动修改目标、启用节点、放宽授权或重试业务执行。旧工具错误保持兼容，新接口可增加结构化错误字段。

不能仅将 MCP 请求转发到 UI 的 send_message：该入口当前会把无 handoff 的输入标为用户，且用户命令具有不同的启动语义。抽取并共用最小的验证/提交逻辑，传入可信来源。

## 12. 验收与实施顺序

验收必须覆盖真实本地 MCP HTTP 与后台状态，不以静态 Schema 或截图替代投递行为：

1. 默认上下文返回正确的节点和条件版本，普通查询不等待账号/插件目录。
2. A 发送到无连线 B，原文/自由 JSON 保留，B 在 A 结束前可运行；A 的 terminal/result 不被发送修改。
3. 同节点 FIFO、不同节点独立；暂停 B 后消息保存但不启动，单独启用仍覆盖项目暂停。
4. B 显式回复，A 在原 Thread 中接收关联输入；A 忙碌时回复排队，等待不靠保持原 Turn 或新增暂停状态。
5. B 正常结束但未显式发送时，不自动广播；无审查要求的任务可以直接完成。
6. 相同 request_id 的并发/重复调用和重启后重试只产生一个接收任务；同键不同内容拒绝；回执丢失可恢复。
7. 数据库提交失败不留下有效消息、输入历史、目标任务或幂等成功；图编辑失败不留下候选节点/边。
8. 普通消息受理后 A 失败不撤回 B；旧 handoff 仍在 A 成功前保持 waiting_source；未知执行不自动重跑。
9. 过期/删除条件、伪造来源、跨项目目标、非法 reply_to、已删除目标均明确拒绝；不会静默改投或自动启用。
10. 附件快照与原路径后续修改相互独立；越界/控制目录/链接路径拒绝；固定快照不被声称为整个工作区审查冻结。
11. 新消息受理后的节点/边编辑不改变旧快照；原配置冲突、忙碌锁定及权限检查仍有效。
12. 原 v1/v2 项目历史和旧工具可继续使用，新工具不自动扩授；来源标签、回复定位和项目时间线通过实际 UI 验证。
13. B 接收 A 的消息后失败，用户确认重试后 B 仍可识别 A、读取相同输入/快照并回复原消息；投递查询显示新尝试，原受理回执不变。
14. 原有 update_workflow 授权不能因全局工具枚举增加而授予编辑者自身未获准的新协作工具；新 operation 保留目标已有流程编辑权与新增授予分开校验。

实施按三个可验证增量推进：

1. 协作闭环：默认上下文、自由发送、持久回执、显式回复、任务入队与最小查询。
2. 工作流编辑：真实能力目录、版本化节点/边修改、关联创建与持久编辑回执。
3. 展示与恢复：分页历史、消息/回复定位、附件快照、迁移及故障恢复的完整验收。

三个增量共同组成首版交付，后两步不因第一步能演示就省略。实现前另写实施计划；本规格不代表代码、真实模型路由或用户界面已经通过验收。
