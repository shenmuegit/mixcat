## 2. 提交成功才产生有效交接

交接、完成和阻塞报告的有效终结记录必须来自成功提交的数据。拟采用以下顺序：

1. 验证 MCP 身份、活动任务、当前轮次、工具权限及参数。
2. 在候选状态准备成果引用、终结记录、交接记录及等待来源完成的接收任务。
3. 将候选状态写入 SQLite 事务。
4. 提交成功后发布变化，并返回持久受理回执。
5. 来源轮次确认成功后，接收任务才成为可调度任务。

提交失败的候选不得进入调度、幂等判断或成功回执。重试需核验已提交记录，不能因为内存曾构造过交接就返回 `accepted: true`。提交成功但回执丢失时，重复调用应取回同一受理结果，不重复创建接收任务。

发布状态需维持活动任务引用的一致性，避免等待原生 RPC 的代码修改已脱离活动状态的旧对象。数据库事务内不等待模型、网络或其他长操作；提交后的调度可从持久状态恢复。

成果文件可先固定再登记。数据库失败时不能将未登记文件当作已交付成果；孤立文件应可核对，清理规则另行设计，不自动删除无法确认归属的用户文件。受理一致性不等于文件系统、数据库和外部工具的全局恰好执行一次。

## 3. 项目运行时初始化与迟到结果

一个项目同一时刻只共享一个有效运行时初始化过程。同项目多个节点首次执行或重启后续接时，等待同一 Promise；不能将“尚未连接成功”解释为必须替换连接。初始化明确失败后才允许重建，旧实例退出有效运行时表并清理其请求归属。

原生事件、断开通知和宿主请求回调都要核对运行时实例身份。旧实例的 disconnect 不能将新实例标为断开，旧请求不能进入新实例的待回应列表。

异步等待结束后须重新核验条件：

- 引擎关闭后不接受新派发、迟到历史写入或重新创建运行时。
- 发送或重试等待期间收到停止命令，不能迟到新增任务并覆盖停止意图。
- 暂停与启用读取节点当前唯一 `status`，旧状态不能覆盖之后的操作。
- 历史读取返回时核对会话、运行时及已到达的实时条目，避免旧内容覆盖新执行。
- 退出时即使某项保存或关闭失败，仍尝试释放其余自有资源并报告失败。

运行时实例身份、关闭标志和过期操作检查是生命周期管理，不是额外的用户暂停状态。

## 4. 控制响应与命令受理

### 4.1 调度分类

| 类别 | 例子 | 拟采用方式 |
| --- | --- | --- |
| 查询与连接 | 历史、能力目录、连接、登录、快照 | 长 RPC 等待不占普通修改串行区间，完成时再核验归属和版本。 |
| 控制与回应 | 四种暂停/开启、停止、审批回应 | 优先受理，不排在慢查询之后；实际状态依据协议确认和最新用户操作。 |
| 普通修改 | 发送、启动、明确重试、节点及条件编辑 | 同项目短状态修改保持顺序，不因无关等待阻塞其他项目。 |
| 退出 | 关闭后台 | 关闭新命令入口，取消尚未开始的排队工作，释放自有资源。 |

停止需取消此前尚未开始且会引发新执行的发送、启动和重试；停止后用户明确发送的新消息是另一动作。已经进入异步执行的修改按第 3 节检查是否失效，不能以等待前的状态继续派发。

控制按钮不能被无关查询的全局忙碌标记禁用。受理暂停和确认暂停是两个时刻，只有匹配的原生中断结果得到确认，才能将执行视为已暂停。

每个节点只有一份权威、多值 `status`。全部暂停、全部开启、暂停节点、启用节点在各自范围内覆盖前一次状态，不增加全局或单节点暂停锁。项目汇总状态与恢复名单不是额外开关。A 运行、B 空闲时全部暂停再全部开启，应只续接 A；B 保持空闲，日后可正常接收交接。

### 4.2 命令编号、超时和恢复

每次用户动作具有独立稳定编号。相同编号及内容不重复执行；同编号不同内容拒绝。不同编号即使正文相同也代表独立动作，不能按文本合并用户消息。

受理状态应可查询为排队、执行中、成功、失败、取消或未知。等待超时后查询原编号，不自动换编号重发，也不将超时显示为已取消。超时、回执保留窗口和回收策略是后续实现参数，本设计不冻结具体数值。

进程内去重只能处理本进程重复请求。跨重启应借助持久化任务或动作关联核对；无法确认的外部操作显示结果未知，核对后才明确重试。是否增加持久命令日志另行确定，不能以短期缓存宣称跨进程恰好执行一次。受理成功与执行完成分别展示。

## 5. 历史来源、流式保存与视图同步

### 5.1 作者来源

| 来源 | 设计要求 |
| --- | --- |
| 用户 | 用户直接提交的正文或附件，显示“用户 → 接收节点”。 |
| 节点 | 有交接记录，保留提交时来源名称，显示“来源节点 → 接收节点”。 |
| 系统 | Mixcat 生成的续接说明，显示“系统续接 → 接收节点”，关联触发它的控制事件。 |
| 未知 | 无法关联以上来源的原生输入，显示“原生输入（来源未知）”。 |

原生 `userMessage` 是协议角色，不直接等同于真实作者。迁移只修正有可靠依据的标签，不改用户正文、交接内容、时间或既有归属；不能追认则保留未知。补读保存原始 native item，不能让原生附加上下文替换用户原话。

### 5.2 保存与恢复

输入受理、任务及节点状态改变、交接提交、正式完成等关键事实，需在返回成功前持久化。纯流式文字和命令输出可以短周期合并；条目完成、关键状态变化及正常关闭时刷新。保存失败进入可见错误与恢复路径，不能吞掉异常或继续宣称已保存。

崩溃可能丢失尚未提交窗口内的文字，可从原生历史补齐；无法补齐时明确缺口。窗口大小须根据响应性、写放大和可恢复性测量决定，不能将其扩展为丢失已受理输入或交接的许可。

广播拟按条目 ID 替换或追加，使用单调版本拒绝迟到结果。没有项目完整基线时补偿读取；切换项目后忽略旧补偿。首次读取和重连取得基线，其他项目更新不能清空当前会话或草稿。普通界面与原生面板使用一致的归属和合并规则。

原型采用项目整体 JSON 快照。设计分两步推进：先合并纯文字写入并推送变化条目，再将长期历史拆成可分页 SQLite 记录，界面按需加载。保留完整历史不等于每次加载全部历史，无需为此引入消息中间件。历史规模、写放大、内存与延迟指标待负载测量后确定。

## 6. 原生能力适配契约

接入层拟记录实际 Codex 二进制、可取得的版本和初始化信息；不能取得时保留未知。基础会话能力与可选宿主能力分开建表，按实际运行二进制生成协议 Schema 并建立版本兼容验证，不能以主分支文档代替运行版本的契约。

原生请求按职责区分用户决定、宿主执行和未支持：

- 命令与文件审批仅接受本次请求提供的决策，旧形式按兼容表处理。
- 用户问题答案关联实际问题 ID，不能回答不存在的问题。
- 权限申请不得超出实际请求范围，并校验 turn 或 session 范围。
- MCP elicitation 区分授权 URL 与表单，按请求 schema 校验，取消与拒绝使用对应格式。
- 宿主能力由对应适配器完成并返回真实结果，不能将用户填写的 JSON 冒充实际操作。
- 未接入的宿主请求明确返回不支持并保留可见证据，不诱导用户猜响应正文。

协议校验位于接入边界，界面提供相应控件，二者不能互相替代。未知业务输出仍完整保存，分类只针对需要宿主响应的协议请求。增加协作不能删除原生可用能力；每项宿主功能分别接入验收，网页预览不等于 Agent 浏览器控制，设计图预览不等于 MCP App UI 双向交互。

能力表至少记录方法或能力、运行版本、必需或可选、宿主责任、可用性依据、未支持提示及验证层级。记录版本或协议测试通过，不等于所有插件、账号组合和业务工具均已可用。

## 7. 项目控制数据的真实边界

当前原型在同一操作系统用户下运行工作台、Codex 和节点工具，属于可信本地协作。Thread、节点 MCP 凭据、目录隐藏、路径校验和网页 IPC 隔离各有作用，不能推导为 Agent shell 无法访问控制数据库或项目登录材料。

节点 cwd 和项目数据继续位于所属项目目录。正式隔离不能通过把数据移至项目外或关闭用户需要的原生能力来满足表面要求。

旧 `workspace-write` 有写入根等选项，不应虚构任意拒绝子路径的 `deny` 字段。[官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference) 新 named permission profiles 可表达更细规则，但与旧配置的关系和平台支持须按运行版本确认，不支持的规则可能被拒绝。[官方权限文档](https://learn.chatgpt.com/docs/permissions)

上述参考不构成跨版本保证。候选策略使用项目内无凭据 fixture 和哨兵，记录二进制、平台模式、有效配置及实际读写，不用真实登录材料做破坏性探针。

### 7.2 后续设计与验收边界

是否需抵御不可信代码、恶意节点或第三方插件，应先明确威胁模型；若需要，操作系统账号、受支持沙箱等方案需独立设计验证。须同时核对控制数据保护、普通工作文件、审批、浏览器、插件、重启恢复和项目内数据归属。目前未选定并验收强隔离方案，不宣称原型已有此能力。

## 8. 需要继续细化、尚未冻结的设计

### 8.1 条件边与选择依据

条件图和实际交接是不同对象。后续 MCP 可让交接关联边 ID、revision、当时条件与选择理由，使边变更后仍能解释历史选择。

条件是建议还是约束、无边能否交接、多条件命中、无匹配、并行目标、汇合仍待讨论。上述追溯字段只是候选，工具名、调用信封与条件语义均未定稿。业务内容保持自由，不恢复固定 `summary`、`verdict` 或业务 Schema。

### 8.2 共享目录中的确定审查对象

共享 cwd 和并行修改要求审查指向确定版本，可采用固定成果记录、文件路径及内容摘要或已有 Git 提交，不能强制为非 Git 项目初始化仓库。

结论关联实际检查版本；检查中发生变化时说明旧结论适用对象，再按待定规则决定是否重审。自动固定输入、变化检测及结论失效仍待细化，不将原型审查对话等同于已实现版本一致性。

### 8.3 每次执行的能力来源

节点 revision 固定配置选择，不能固定 skill 文件和插件内容。拟为执行保存可核实来源：请求模型、原生实际模型回执、Codex 版本、选中 skill 路径及内容摘要、插件来源与可取得版本。

来源记录待实施。无法确定时标未知，不把 manifest 版本冒充运行缓存确认，不把 manifest 摘要冒充整包摘要，不因来源未知而擅自禁用能力。摘要不覆盖原文，也不代表环境已冻结或备份；是否保留内容副本与范围另行设计。

### 8.4 项目、笔记与知识库

已确认导航为左侧“项目／笔记／知识库”，中间项目卡片，点击卡片进入工作流。该方向只有静态视觉原型；以下关系待讨论，不是已实现服务。

| 对象 | 待细化职责 | 数据归属原则 |
| --- | --- | --- |
| 项目 | 管理目标、节点、执行、会话、成果及审查。 | 用户选定的项目根目录。 |
| 笔记 | 保存可编辑内容，可引用条目或成果版本，不覆盖原始会话。 | 每份有明确归属，项目笔记留在该项目。 |
| 知识库 | 组织资料、笔记和来源索引。 | 明确自身所属项目或根目录，不默认使用系统目录或无归属全局库。 |
| 引用 | 关联项目、节点、条目或成果及版本，区分引用和复制。 | 跨项目访问、离线、搬迁、失效和复制行为另行确定。 |

是否独立存在、跨项目授权与搜索、源内容更新及复制后所有权仍待讨论，不能由导航推导任意项目自动共享资料。

## 9. 后续实施验收清单

以下均为后续验收要求，**本次文档修订不把任何一项标为已通过**。原型历史证据见 [功能设计第 14 节](2026-10-19-mixcat-client-functional-design.md#14-已有验证证据及其限度)，权限实验见第 7 节。

| 设计项 | 必须覆盖的场景 | 判断依据 |
| --- | --- | --- |
| 提交一致性 | 数据库失败、提交后回执丢失、同调用重试、提交后重启、来源失败。 | 未提交不成功不调度；成功只有一份接收任务，来源成功后只释放一次。 |
| 运行时单实例 | 并发初始化与恢复、失败后重建、旧断开和请求迟到、退出时 RPC 返回。 | 一个有效项目客户端，旧实例不写新状态，关闭后不派发。 |
| 控制响应 | 慢查询期间四控制、停止、审批；重复编号或不同正文；超时与重启。 | 控制及时受理，四操作覆盖唯一状态，不重复派发；未知明确核对，原空闲节点不启动。 |
| 作者来源 | 用户、节点、续接、未知输入，迁移、补读及节点改名。 | 原话不变、来源不伪造，系统正文不归用户，历史归属保留。 |
| 历史保存与同步 | 连续输出、保存失败、完成与退出刷新、迟到快照、切项目、缺基线、长历史。 | 关键事实提交后才成功；无倒退串项目，缺口可解释；测量后再定性能参数。 |
| 原生能力契约 | 合法、越界、取消回应；未知宿主请求；版本未知；可选能力缺失。 | 符合实际版本，不扩大授权、不虚构执行，基础与可选能力分开展示。 |
| 控制数据边界 | 目标平台 fixture 读写；工作文件、审批、浏览器、插件、重启与数据归属。 | 实际权限和结论可复核，保护与正常能力同时验证；未满足前不称强隔离。 |

真实模型工具中断副作用、断电或磁盘损坏恢复、长期负载、全部插件与账号组合需另行验证。受控 fixture、原生命令实验、真实模型和桌面像素验收属于不同层级，不能互相替代。
