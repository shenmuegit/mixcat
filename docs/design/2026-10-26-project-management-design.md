# 项目管理与既有工作流接入设计

日期：2026-10-26。关联 [GitHub Issue #13](https://github.com/shenmuegit/mixcat/issues/13)。

**状态：2026-10-26 用户确认继续实施。** 本文为实施规格；各项功能是否通过验收以实施记录为准。

## 1. 已确认的目标与方案选择

用户要求在客户端增加 TodoList、Issue 和文档管理，TodoList 支持树形结构，三者通过类似 `@` 的操作互相引用。用户先后明确“内部管理即可”“我们需要先固定方案”，并认可“用户与节点共同维护”。

用户进一步明确：Mixcat 管理的现有项目都是测试项目，可以清空任何其他数据，只需要保留节点和条件边；本次不做旧数据迁移。验收直接使用当前项目或本次开发工作树，不另建独立测试项目，也不以其他项目目录作为前置条件。清空授权用于切换新版本时的一次性测试数据重置，不把正常启动改成清空数据。

采用用户与节点共同维护同一份项目数据的方案：用户从客户端操作，节点通过现有 MCP 接入点操作；工作交接继续沿现有条件边进行。项目管理用于记录工作、资料与证据，执行过程仍由现有消息队列、独立会话、暂停恢复和人工核对机制承载。

| 考虑过的方案 | 收益与代价 | 选择 |
| --- | --- | --- |
| 仅供用户管理，节点只读取或接收粘贴内容 | 改动较小，但工作进展需要人工重复登记 | 未采用 |
| 用户和节点共同维护，沿已有工作流交接 | 工作项、资料和执行可以相互追踪，需要接通管理接口及关联元数据 | 用户已认可 |
| 待办状态与依赖直接驱动调度 | 能自动触发节点，但需要重新定义调度、并发、暂停和核对关系 | 首版不包含 |

下文的字段、状态、默认值、接口分工和异常行为作为本次实施依据。实现可以调整内部组织，但不能静默改变这些可观察行为。

## 2. 当前系统与接入点

- `ProjectStore` 将各项目状态保存在该项目的 `.mixcat/state/workflow.sqlite`。已有 `TaskView` 是一次 Agent 执行，关联原生 Thread、Turn、输入输出与重试，不是业务待办。
- 节点通过自己的 `edge_<hash>` 工具发送自由 JSON 内容；目标由条件边绑定。消息、接收任务、来源历史与回执一起持久保存。条件边不会被程序再次解释为业务判断。
- `get_project_context` 提供项目、自身节点、当前执行、来信、条件边与核对信息。它是提供当前工作项摘要的接入点。
- 人工核对已经有固定版本、附件快照、显式用户决定与待核对执行。文档模板已经生成真实项目文件，节点以项目目录为工作目录。

依据：[动态条件边 MCP](2026-10-24-dynamic-edge-mcp.md)、[人工核对](2026-10-22-human-review-design.md)、[Web 产品工作流与文档协作](2026-10-22-web-product-team-workflow.md)。

## 3. 领域对象与数据归属

| 对象 | 含义与权威数据 | 与其他对象的关系 |
| --- | --- | --- |
| Todo | 一项业务工作；结构、状态和负责人由项目管理保存 | 一个可选父 Todo；多个子 Todo；多个 Issue、文档与执行关联 |
| Issue | 问题或变更需求；描述、验收条件、讨论与处理结论由项目管理保存 | 与 Todo、文档相互引用；关闭不自动完成待办 |
| Document | 已纳入管理的项目文件；正文以实际文件为准，注册身份与路径映射由项目管理保存 | 可被工作项、评论、消息、核对包引用 |
| Runtime task | 一次实际执行；现有引擎记录排队、运行、暂停、失败和结果 | 可关联一个主要 Todo，以及其他工作项、资料；同一 Todo 可关联多次执行和多个节点 |
| Reference | 从一处正文或明确关联指向另一个对象 | 表示引用，既不形成父子关系，也不形成调度依赖 |

三类管理对象共用稳定的 `id`、所属项目、显示编号、标题、创建时间、修改时间、修订号和归档标记。显示编号分别为 `T-12`、`I-7`、`D-3`，项目内按类型递增，不回收已归档编号。内部 ID 承担身份识别，编号只服务于展示和搜索。

Todo 和 Issue 有 Markdown 描述、验收说明、优先级（低／普通／高）、可选负责人。负责人可以是当前用户或本项目节点；不设置时为未分配。节点归档后保留历史负责人信息，显示其已归档。负责人表达责任分工，不授予额外权限、不触发执行。

Issue 提供评论。每条评论有独立身份、作者来源、时间和正文，支持引用；首版评论追加发布，更正通过新评论说明，以保留讨论证据。

管理元数据、操作记录、幂等回执和可重建的引用索引由同一项目 SQLite 管理。文档正文不再有另一份可独立编辑的数据库副本。现有工作记忆 `.planning/` 保存调查、步骤和下一步；业务进度以 TodoList 为准，计划文件引用工作项而不维护第二套实时业务状态。已有 Markdown 勾选项不自动变成系统 Todo。

## 4. 树形 Todo 与业务状态

Todo 状态为未开始、进行中、阻塞、完成。Issue 状态为待处理、处理中、已关闭，类型为缺陷、功能改进或需求。关闭 Issue 需要填写处理说明；标记 Todo 完成需要完成说明，可引用测试、文档、评论或执行结果。说明记录事实，不由程序推断其内容已通过验证。

- Todo 支持多级创建、展开折叠、同级排序、调整父项；提供拖拽和等价的键盘／菜单操作。
- 每项只有一个父项，父项必须是同项目 Todo；禁止自引用和祖先循环。引用文档或 Issue 不会改变树结构。
- 父项展示其有效叶子项的完成数／总数，不把中间父项重复计入分母。归档子树不参与当前进度；没有有效子项时按其自身状态显示，不展示虚假的 `0/0 = 100%`。
- 父项完成是显式操作。仍有未完成的有效后代时，拒绝该完成请求并指出未完成项。叶子全部完成也不自动完成父项，以容纳集成与整体验收。
- 在已完成的父项下面新增未完成工作，或将未完成工作移入该分支前，需要先显式重开对应已完成祖先；操作不得悄悄改变已完成记录。重开子项时，同一次明确操作列明并重开必要的已完成祖先。
- 归档 Todo 明确作用于整棵子树；归档前展示影响。恢复子树时一并恢复必要的祖先，避免恢复出隐藏孤儿。归档状态与完成状态分开记录。

用户和拥有管理写入能力的节点都可显式维护业务状态；节点职责由项目说明约定，不按“产品经理”“测试”等名称写死。每次变更记录修改前后值、来源与理由。

运行状态与业务状态分别呈现。收到消息、Turn 完成、`complete_task`、节点失败或暂停都不自动更新 Todo／Issue 状态。普通引用、负责人变更与文档保存也不启动节点。关联对象已归档时，历史执行仍可查看；要继续维护该对象，应先明确恢复。

## 5. 文档管理与并发编辑

首版管理项目内的 UTF-8 Markdown 文件，提供新建、纳入已有文件、目录／路径浏览、标题修改、文件重命名／移动、编辑、预览、搜索和归档／恢复。新建默认位于项目 `docs/` 下，用户可选择项目内允许的位置。已有文件先注册再获得稳定 Document ID；再次纳入相同规范化路径返回原对象，避免重复身份。

文档归档只是归档管理对象，不删除文件；恢复后沿用原 ID。标题或客户端内文件移动不改变 ID。外部工具移动文件后原对象显示“文件缺失”，由用户或节点通过显式重新关联路径找回；不能仅凭同名文件猜测身份。重新关联需展示或返回旧路径与新路径，核实目标仍在本项目内。

读取返回内容、元数据修订号和正文哈希。保存必须携带读取时的修订号与哈希。客户端与 MCP 的受管写入按文档串行执行；提交前重新检查文件和版本。遇到外部变化则拒绝覆盖，返回最新内容／版本，保留用户草稿，让修改者重新合并后提交。打开、切回文档和手动刷新会核对真实文件；后台刷新不替换尚未保存的草稿。

保存采用项目内暂存与原子替换，文件写入和元数据更新之间使用可恢复的操作记录；失败不能报告成功，重启能够区分已提交、待恢复与冲突。恢复时不得用旧正文覆盖已经出现的外部新内容。具体恢复实现由构建者选择，但必须提供故障注入证据。

原生工具仍可直接改项目文件。这类外部变化在索引刷新时标记为“外部修改”，不能猜测作者；只给当前观察到的字节建立修订记录。哈希检查不等同于锁住任意外部编辑器，也不宣称已经提供多进程强隔离。

所有路径在读写时校验真实项目范围、祖先链接和目标类型；拒绝路径穿越、目录联接、符号链接及会让编辑影响项目外文件的链接。内部控制目录（`.mixcat`、`.runtime`、`.git`）不作为用户文档管理目标。Markdown 预览不执行原始 HTML、脚本或危险 URL。

## 6. 统一 @ 引用

待办描述与验收说明、Issue 正文与评论、文档正文、节点输入框共用引用选择器。输入 `@` 后搜索当前项目的三类管理对象，可按标题或显示编号匹配，结果展示类型、标题与状态；支持方向键、回车和 Esc。默认候选隐藏归档对象，可通过明确的归档筛选找回。

引用以标准 Markdown 链接保存，例如 `[@T-12 登录接口](mixcat://<project-id>/todo/<id>)`；方案中的 URI 是应用内部引用格式，不要求注册操作系统协议。链接保存稳定身份，当前界面解析时展示最新标题与状态。历史消息保留原始文字，预览可补充当前状态，不重写历史原文。

三类对象均可互相引用，也可同类型引用。引用解析遵循 Markdown 结构，代码块、行内代码与转义文本中的示例不会被当作实际关系。服务层统一提取、去重和更新引用，客户端显示同一结果。

详情显示“引用了”与“被引用”，并能定位来源工作项、文档或具体评论；消息中的引用可以跳回对应会话记录。删除一处正文引用后，该处反向引用随之移除，历史消息和其他引用继续存在。文档在文件变化后重新索引，索引进度或读取失败明确显示，不能声称尚未扫描的文件已经完整。

点击已归档对象可读其历史信息，操作前可恢复；引用不存在或文件缺失时显示失效状态并保留链接原文。粘贴含未知链接的 Markdown 不丢弃原文；显式工作关联参数则必须校验目标存在且属于本项目。首版不跨项目解析引用。

## 7. 用户与节点使用同一组管理接口

客户端命令与 MCP 工具调用同一项领域操作，统一校验修订、父子关系、文件路径、归档状态和持久化。MCP 侧拟提供三个通用工具；不为模板中的各角色生成不同的业务工具。

| 接口 | 行为 |
| --- | --- |
| `search_project_items` | 按类型、关键词、状态、负责人、归档状态搜索，分页返回摘要，不一次注入全部文档 |
| `get_project_item` | 按稳定 ID 获取当前对象、版本、引用与反向引用；正文和长列表按需读取／分页 |
| `update_project_item` | 按明确操作创建、编辑、调整树结构、归档／恢复、评论、纳入或移动文档；各操作只接受自身字段 |

项目身份和写入作者来自已认证的 MCP 节点及原生 Thread／Turn／call，不接受模型指定另一项目或伪造作者。写入需要有效活动执行；同请求的已受理重放按原回执返回。每次写入使用稳定 `request_id` 和预期修订号；相同请求内容重试不重复创建或评论，不同内容复用请求号报冲突。客户端使用已有命令编号机制，并持久保存管理操作的受理结果以应对重启和丢失回执。

**建议默认：** 新建项目／节点以及本次重置后恢复的节点默认提供上述查询和写入工具。恢复节点时沿用保存的配置并补入这三项新能力；此后尊重用户在节点工具设置中的开关，不在每次启动时重新补回。运行中的工具配置变动仍在节点下一轮刷新，不中断当前轮。管理工具权限只约束该入口，不假装限制节点已有原生文件工具。本次不实现旧节点能力迁移。

`get_project_context` 增加当前工作关联的摘要、可用管理工具提示与查询入口；不把整个待办树、所有 Issue 和所有文档塞入每轮上下文。没有工作关联的普通对话仍能使用管理工具，查找并维护需要的对象。

## 8. 沿现有条件边传递工作关联

用户发送命令和条件边消息增加可选的 `work_context`，包含一个可空的 `primary_todo_id` 和一组类型明确的 `references`。普通正文保持自由文本或自由 JSON；`@` 插入的引用和显式主待办由输入框形成结构化关联。

- 用户从 Todo 点击“交给节点”时打开现有输入框，预填主要工作项和用户选定的资料；用户实际发送时才创建执行。该入口仅用于 Todo，Issue 和文档通过引用参与工作流，不提供直接发送入口。普通输入没有关联时不从节点的上一轮猜测工作项。
- Agent 沿条件边交接时可以显式提供完整的 `work_context`。未提供时，普通发送继承当前执行的关联；关联回复优先继承被回复消息的关联。明确传入空对象集合可以开始不关联原工作的对话，避免无法脱离旧工作项。
- 接收目标仍由所调用的条件边绑定。来源／目标的查询、暂停、FIFO、重复请求与回执处理复用已有机制。
- 受理时将消息、已解析的工作关联、接收执行和来源历史一起提交，失败则整体不受理。保存引用目标当时的标题、修订号和文档哈希作为观察信息；它们不等同于正文快照。
- 重放请求首先恢复原有受理结果，不因后来内容变化、引用归档、边改动或继承上下文变化而重算。显式修改过的请求仍报冲突。
- 接收任务、暂停恢复和重试保留原关联。节点上下文并列给出受理时的观察版本和当前版本；内容变化可见，不静默替换原消息。需要固定正文时使用附件快照。

一个 Todo 可查看所有关联执行、节点、消息和成果；一次执行可查看其主要 Todo 和其他引用。新增这项关联不把 Todo 自动变成队列任务，也不按树形结构生成条件边。

## 9. 既有人工核对与材料版本

核对提交通过 `item_ids` 携带选定的 Todo／Issue／Document 引用，通过 `comment_ids` 显式选择 Issue 评论。对于作为核对依据的管理对象，宿主在受理时捕获明确版本：Todo／Issue 的描述和验收说明以固定序列化材料纳入包，Document 使用既有文件附件快照。选定评论固定其 ID、所属 Issue、正文、作者和时间；不递归抓取整张引用网络。

核对包记录这些对象的版本与哈希，展示提交时内容与当前内容的区别。管理对象材料变化参与已有的材料陈旧检查：旧用户决定仍属于旧包，新材料需提交新版本；不由 Agent 伪造批准，不把新内容静默替换进旧批准。

业务状态、负责人和新增非材料评论等进度变化不应使一个基于相同需求正文的核对包失效；材料指纹覆盖选定正文、验收条件及文档字节，避免用所有元数据修订号造成无关失效。归档作为状态显示，核对的历史快照仍可读。

核对依旧约束现有执行派发，保存工作项或标记完成不解除该约束。界面分别显示业务状态与核对状态；是否需要人工验收由项目已有配置和任务要求决定，不对所有 Todo 新增强制审批。核对通过也不自动关闭 Issue 或完成 Todo，由责任人或节点结合实际结果明确更新。

## 11. 测试项目重置、范围与验证条件

本次按全新的数据格式初始化，不实现旧数据库、旧会话、旧消息或旧管理记录的迁移。用户授权现有受管测试项目清空其他数据，唯一业务保留对象是当前有效节点及条件边：

| 保留对象 | 必须保存和恢复的内容 |
| --- | --- |
| 节点定义 | 稳定 ID、名称、职责指令、模型、工具、skills／plugins 选择、结果格式、画布位置、配置修订号和 planId 等定义字段 |
| 条件边 | 稳定 ID、起终点节点 ID、方向、完整条件文本、修订号以及已有连线布局 |

项目目录与承载节点图所需的最小项目标识作为恢复容器。旧 Thread 绑定、节点运行状态、执行／消息队列、会话历史、回执、核对规则与记录、附件快照、工作记忆、生成文件及其他测试数据均可以清空。该范围是 Mixcat 管理的测试数据；在当前源码项目或开发工作树中验收时，不能将 Mixcat 自身源码、设计文档或 Git 元数据当作可清空的测试数据。恢复后节点处于空闲状态，首次执行创建新会话，不连接已清除的 Thread。保留的 planId 对应空白工作记忆按现有机制重新初始化，不引用已删除的计划内容；插件和能力运行文件按现有配置重新准备。

重置属于本次发布切换动作，不增加通用重置产品功能，也不在每次启动或读取失败时自动删库。执行顺序为：核对受管项目清单和真实绝对路径；在各目标项目内持久保存并核验节点／边保留清单；正常停止目标执行并确认写入进程已退出；清理已授权的测试数据；按新格式初始化并恢复节点图；核对定义及边引用完整性，再开展验收。保留清单在恢复成功前不得删除。无法确认执行已停止或保留清单完整时，不进入删除步骤。

清理仅作用于逐项核实的测试数据路径，不根据共同父目录递归删除。当前项目或开发工作树承载验收时，只清理其中已确认的 Mixcat 测试状态和本次生成的验收数据，不能递归清空仓库／工作树根目录。共享账号、全局插件、其他项目及宿主源码不属于该清理范围；无法区分受管测试数据与源码时，先核实具体路径再执行。项目内保留清单和恢复资料遵守所属项目路径规则。

新格式运行后的项目仍需具备项目隔离、归档恢复、重启持久化和执行历史查询；以后正常移除项目遵循现有目录与历史保留行为。本次测试环境清空授权不扩展为未来版本可以随意清除用户数据。保存成功必须代表可持久恢复，不能只更新前端缓存。

所有工作数据、文档暂存、恢复记录和测试产物留在所属项目内。实现沿仓库 Issue → 分支 → 测试 → 双轴审查 → PR → 合并流程进行，最终按当前版本构建并安全重启实际客户端。

首版包含用户与节点共同维护、树形待办、内部 Issue、Markdown 文档、统一引用与反向引用、消息／执行关联、核对材料关联。GitHub 同步、云协作、自动任务调度、跨项目引用、原生工具强隔离和通用版本控制系统不在本次范围。

| 验证边界 | 必须证明的行为 |
| --- | --- |
| 一次性重置 | 当前节点定义、条件边及布局精确保留；旧会话／执行数据清除；新会话正常创建；清理路径不越界；重置中断时保留清单仍可恢复 |
| 客户端命令／重开项目 | 三类对象 CRUD、归档恢复、项目隔离、新格式重启持久化及执行历史查询；正常重开不再次清空 |
| Todo 公共操作 | 多级树、排序和移动、循环拒绝、叶子进度、父项完成约束、归档恢复与竞争编辑 |
| 文档公共操作 | 已有文件纳入、真实文件编辑、移动身份稳定、外部变更冲突、路径与链接拒绝、保存中故障及恢复 |
| 引用解析与查询 | 三类互引与同类引用、代码示例排除、评论来源、删引更新、归档／缺失标识、标题变更 |
| 真实 loopback MCP | 查询和写入、节点身份、撤销能力、修订冲突、受理回执重放、来源记录；不伪称真实模型已使用 |
| 条件边与执行 | 上下文继承／覆盖／清空、回复、暂停队列、重试和断连后重放，消息与执行关联的原子保存 |
| 核对边界 | 已选材料固定版本、正文变化陈旧、无关状态变化不误失效、现有等待与人工决定规则 |
| 实际 Electron | 树操作、编辑保存、键盘 @ 选择、跳转／返回、反向引用、草稿保护、冲突提示、原生面板隐藏 |
| 最终交付 | 相关测试、类型检查、构建、一次完整回归、两个审查轴；实际客户端安全重启与版本证据 |

上述都是待实现、待验证的验收条件，不是已通过结果。技术故障与实现取舍记录在 Issue 和实施计划中，本文维护产品行为与设计决定。

## 12. 确认采用的默认规则

1. 用户与具备写入工具的节点都能直接维护业务状态，并记录来源和说明；不新增逐项用户批准。
2. Todo 完成与 Issue 关闭采用明确操作，运行结束与核对通过不会自动完成业务工作。
3. 业务进度归 TodoList，文档和 `.planning/` 引用它；现有文件不自动导入为任务。
4. 条件边消息按第 8 节默认携带工作关联，需要脱离原工作时显式清空；持久化版本与引用内容快照各有明确含义。
5. 新建及本次重置恢复的节点默认获得新管理工具，此后尊重各节点开关；本次不做旧数据或旧能力迁移。

用户在确认上述修订后表示“可以继续了”，据此进入实施。第 11 节的测试数据清空授权与节点／边保留范围，以及第 14 节直接在当前项目或开发工作树验收，均已确认。

## 14. 当前项目或开发工作树作为验收基座

直接在当前 `G:\code\mixcat` 项目或本次实际开发使用的工作树中构建、运行和验收，复用已有节点与条件边；不另建独立测试工程，不复制或克隆一个额外仓库，不要求切换到 `mixcat-test`。如果使用开发工作树，其实际路径也必须位于本项目根目录内。测试状态、日志、截图和验收文件放在当前项目／工作树内明确划定的数据目录；产品代码不硬编码本机路径。隔离测试所需临时数据同样在所属项目内生成，不要求额外搭建测试项目。

在按第 11 节完成一次性重置后，使用保留下来的真实节点与条件边验收以下闭环：

1. **用户建立工作。** 在实际客户端新建一个验收父 Todo 及多级子项、一个内部 Issue 和一份验收文档，设置相互引用，验证树操作、搜索、引用预览与反向引用。
2. **节点维护同一份数据。** 从待办进入一个现有节点的输入框，发送有明确范围的验收任务；由真实节点通过管理 MCP 查询、修改对象、发表评论并更新文档，客户端显示对应结果及来源。
3. **沿已有边交接。** 选择确有出边的节点对，原节点沿该边发送当前工作与资料；接收节点在原有节点职责下读取工作关联，维护相同对象并记录结果。只有已有反向边时才验证关联回复，不为凑验收路径临时改造节点图。
4. **检查边界行为。** 验证显式业务状态更新、父项完成约束、归档恢复、外部文件改动后的保存冲突和固定核对材料。重置后核对记录为空，需要验证核对场景时在测试项目明确配置一条测试规则并提交真实材料；自动化决定只算受控测试，实际人工批准只由用户作出。
5. **检查恢复。** 等待或正常暂停活动执行后，安全重启实际客户端，核对节点图、验收工作项、引用、讨论与执行关联均能恢复，确认启动不会再次执行数据清空。

场景中的节点只需完成小范围的验收文档与管理操作，不要求额外实现一个示例业务应用。项目内保存受理回执、必要日志、界面截图和实际结果；明确区分自动化／受控 MCP 测试、真实节点工具调用、实际客户端交互和用户人工决定。仅有界面可见或数据库记录，不视为真实节点已经成功调用。
