## 1. 目标与已确认规则

用户希望在 Agent 协作中增加人工核对，例如核对产品需求方向和 UI/UE。核对对象应是具体方案及版本，记录用户意见后回到对应原会话继续工作；不能用 Agent 自评、节点启用或沉默代替用户认可。

建议首版为 Web 产品模板提供两个可调整的核对点：产品需求方向和 UI/UE 方案。人工核对不增加固定的“人工 Agent”节点，也不替代测试或独立 Agent 审查。已有项目不自动增加核对要求。

用户已选择阻断依赖阶段：相应核对通过后，Mixcat 才派发依赖该方案的后续工作；不依赖的调查、需求澄清和测试准备可以继续。

首版不增加“只提醒仍继续”的运行选项。正式通过只来自用户对具体版本的核对操作，Agent 自评、普通聊天、节点启用和等待超时均不能代替。

## 2. 三种接入方式

| 方式 | 价值 | 限制 |
| --- | --- | --- |
| 项目内持久核对事项（推荐） | 固定待核对版本、保存用户决定、重启后恢复，可由引擎检查后续派发条件 | 需要扩展现有状态模型、MCP 和界面 |
| 仅使用 Codex 原生提问 | 复用当前提问卡片，适合临时澄清 | 当前待回应请求保存在运行内存，依赖原生请求生命周期；不能直接当成跨重启的业务核对记录 |
| 仅在职责或文档中提醒 | 改动最小，可以先试协作习惯 | 没有确定的核对事实与调度约束，Agent 可能跳过或误解 |

复用现有 WorkflowEngine、项目 SQLite、原始会话历史、固定附件及工作面板，不新增审批服务、用户账号体系或消息中间件。Codex 原生权限审批及 hooks 信任继续走各自已有流程。

## 3. 默认协作位置

| 核对点 | 谁整理并提交 | 用户主要看什么 | 推荐的自动派发条件 |
| --- | --- | --- | --- |
| 产品需求方向 | 产品经理；需求分析提供规则与验收条件 | 目标用户、解决的问题、核心流程、本轮范围、验收条件与未知项 | 架构师、设计和后端依赖该核对；产品经理、需求分析仍可准备和澄清 |
| UI/UE 方案 | UI/UE 设计节点 | 页面或原型、主要交互、加载／空白／错误状态、视觉方向 | 前端实现依赖需求方向及该核对；后端可依据已通过的需求继续工作 |

测试节点可提前梳理场景，不因 UI 尚未确认而整体禁止运行。正式联调验收关联已经采用的需求与 UI 版本。

默认规则以节点 ID 和明确配置表达，不靠节点名称或连线上的自然语言推断。连线仍是指导关系；无连线发送同样经过已配置的派发条件。用户可在项目内查看和调整核对点及其适用节点，首版不增加独立的图形审批节点类型。

## 4. 阻断范围与原有控制

规则作用于 Mixcat 管理的相关后续任务派发：输入可以先持久受理，待依赖核对通过后才执行；回执清楚区分“已受理”和“等待人工核对”。普通消息、旧 handoff、用户直接输入、恢复队列和重试都核对目标节点的依赖，不能换一种发送方式就绕过。

依赖未满足的接收任务使用 waiting_review 任务状态，保存明确依赖及输入，不占用原生 Turn。它不进入可执行 FIFO 队首；未受该核对约束的节点照常处理可执行任务。通过后在同一提交中解除相应任务等待，按原接收顺序加入可执行范围。此次扩展的是任务状态，不新增节点暂停状态，也不让一个待核对任务阻塞整个项目。

节点保留现有一份权威多值运行状态。核对事项是业务记录，不增加项目暂停锁或第二份节点启用状态；“全部开启”和“启用节点”不会生成通过决定，也不会消除业务依赖。用户明确暂停的节点，核对通过后仍按现有暂停与队列规则处理。

用户仍可向任意节点发送任意内容，原文与来源正常保存。若目标节点的前置核对未满足，该输入同样等待；发送本身不代表通过，也不让 Agent 猜测正文是在咨询还是授权越过核对。用户可在当前提交事项中提出修改，提交责任节点继续处理；已经运行的原生权限请求和提问仍可正常回应。界面同时展示业务核对状态与实际执行状态，不能把“等待核对”冒充正在调用工具。

核对等待不占用一条长时间挂起的 MCP 请求。来源节点提交事项后可以结束本轮或处理独立工作。项目仍有必需核对未完成时，汇总界面不能仅因所有原生 Turn 结束就宣称产品已完成。

此机制控制 Mixcat 管理的协作流程，不关闭 Codex 原生工具，也不宣称能够冻结共用工作目录或阻止 Agent 原生文件操作。

## 5. 核对事项与版本

项目配置保存核对点 ID、名称、提交责任节点、适用节点、上游核对依赖和配置修订号。既有节点及项目迁移不默认获得新的工具授权或业务约束。

配置校验同项目有效节点、完整依赖引用及无环关系；保存使用修订号防止旧界面覆盖新规则。首版按明确适用节点执行约束，不通过模型猜测任务语义。

每次提交保存独立核对事项：

- 项目及核对点、版本、真实来源节点／任务／Thread／Turn，以及稳定请求编号。
- 标题、自由正文、要用户判断的内容及固定附件快照；文字、Markdown、图片或设计资源均可，业务内容不强制统一 Schema。
- 提交时依赖的上游核对版本、配置修订和包内容哈希。
- 状态、用户决定、原始修改意见、时间及对应续接记录。

状态建议为 pending、approved、changes_requested、withdrawn、superseded。状态属于核对事项；不是新增五种节点运行状态。终结版本的正文、附件和用户决定不覆盖；修改后创建新版本，旧版本继续可查。

用户通过的是当前展示的固定包，不是一个随文件改动而变化的路径。提交包有源文件引用时，决定前核对其当前版本；如果内容已变化，显示差异并要求提交新包，不把旧按钮应用到新内容。网页链接可供辅助查看，但可变网页本身不作为固定版本证据。

需求核对被新版本替代时，依赖旧需求的 UI 核对不能自动用于新需求；重新检查其上游版本关联。只检查明确提交的材料和依赖，不因任意代码、日志或无关文件变化而让全部核对失效。

变更发生前已运行的任务、已发送内容和外部副作用保留原事实，不倒写历史或声称已撤销。新派发检查当前依赖；正在运行的工作提示其依据可能过期，由用户决定是否使用现有停止操作。

## 6. 用户操作与回流

项目状态栏显示“待人工核对 N”，点击打开该项目的事项列表；节点会话中也展示所属事项及历史。复用当前白灰布局与文件／网页／图片工作面板。

核对卡片展示来源节点、版本、提交时间、正文、附件和上游依据。核心操作为“通过”和“提出修改”；后者填写自由意见。待定可以保持原状，不把关页、超时或节点恢复理解为通过。

- **通过**：持久保存该版本的用户决定，向提交者原会话排队投递一次带来源和版本的系统通知，并唤醒已受理且依赖已满足的队列。
- **提出修改**：持久保存原始意见，向提交者原会话排队投递一次修改任务，继续阻断依赖该核对的自动工作。提交者可联系原责任节点，修改后提交新版本。
- **重复点击／丢失响应后的重试**：复用决定命令编号，返回已有决定，不生成重复续接。旧窗口、不同版本或冲突决定不能覆盖新事实。

通知遵守现有 FIFO 与暂停语义：忙碌时排队、暂停时保留，用户启用后再执行。核对通过不自动放开用户暂停，也不自动再创建整套下游任务。

撤回只结束该事项，不等于通过；仍生效的必需核对规则不能因撤回自动满足。“停止本轮”可取消其范围内的 waiting_review 任务，之后通过事项不会复活已取消任务或补发历史操作。

## 7. MCP 与身份边界

建议增加两项协作能力，工具名在实施计划中固定：

| 接口 | 行为 |
| --- | --- |
| request_review | 指定核对点，提交标题、自由正文和附件；来源由当前会话确定。提交后返回稳定事项／版本及 pending 回执，不等待用户在线 |
| get_review | 按事项或自己生成的请求编号，读取核对状态、准确版本、用户意见及后续关联 |
| get_project_context 扩展 | 返回项目已配置核对点、自己适用的依赖和待处理事项摘要；不默认加载全部正文 |

相同来源／请求编号与相同内容幂等返回；同编号不同内容报冲突。复用已有固定附件、调用身份、持久回执与候选状态提交模式。

通过／退回只由可信桌面用户命令提交，MCP 不提供 approve_review，也不允许 Agent 用 update_workflow 删除用户配置的核对要求、改审批状态或伪装用户。普通聊天“好的”不由模型猜测为正式通过。

普通文档、planning-with-files 的阶段状态、Agent 的声明、Codex 原生工具审批和 hooks 信任都不是业务核对的权威决定。原始反馈与决定由项目数据库和会话事件保存，规划文档可引用其编号。

## 8. 持久化、恢复与兼容

继续使用项目 SQLite 和先提交后发布的模式。用户决定、依赖变化和唯一续接任务在同一候选状态提交；存储失败不显示通过、不通知、不放行。保存未知时先查原命令或事项，不盲目重复操作。

重启后仍显示未决事项，不把曾经打开的窗口视为用户已经查看。已记录决定不会因恢复自动再投递；原生执行结果未知仍沿用 needs_reconciliation，人工通过不授权自动重放外部副作用。

接收任务保存它所依据的实际核对版本。新包替代旧包时，不把新版通过结果默默套用到旧输入；相关未派发任务显示版本过期，保留原输入供用户取消，或由来源节点以新请求重新交接。开始派发及异步准备完成后的恢复／Turn 边界都重新检查依赖，防止准备期间发生的替代或配置变更被忽略。

核对点尚无提交时，任务保存“等待首次提交”的明确依赖，首次提交时再关联该版本；它不能因当前没有事项就视作已通过。随后替换版本仍遵守旧输入不能自动套用新版本的规则。

节点删除应保留其核对历史；若它仍是待核对事项或生效规则的责任节点，先要求用户撤回事项或调整责任，不能静默删除后改投其他节点。规则和节点编辑共用当前配置版本校验。

不新增服务、外部通知、多用户权限、自动审美评分、默认二次独立审查、任意定时催审或全工作区版本冻结。

## 9. 实施影响面与验收

影响现有 shared types、ProjectState／存储迁移、WorkflowEngine、MCP 工具定义与授权、项目上下文、历史事件、Web 模板默认配置，以及 Workbench 的状态栏和核对卡片。已有原生提问／审批卡片继续保留原协议含义，不改造成业务审批记录。

实施前写独立计划，并至少覆盖：

1. 新 Web 模板的两个核对点及旧项目零自动扩权／零自动阻断。
2. 自由正文、图片／文档固定版本、真实来源和原始意见保存。
3. 未通过时相关消息已受理但未派发；独立节点仍能工作，无边发送及旧 handoff 不绕过。
4. 通过或修改意见只续接一次原会话；暂停、忙碌和四种控制不伪造决定。
5. 多窗口版本冲突、重复提交、重复点击、丢响应查询、源文件变化及上游版本替代。
6. 存储失败、项目重启、待核对任务和原生未知执行不丢失、不自动放行。
7. Agent 不能批准、撤销用户规则或冒充用户；节点删除保留历史并处理责任引用。
8. 真实 Electron 显示核对材料，用户点击通过／提出修改，检查对应原会话、队列和历史；再用极小产品验证需求与 UI 两次人工介入。
